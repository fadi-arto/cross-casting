# Prompt للـ Frontend — Cross-Casting Review UI

> انسخ كل ما تحت هذا السطر وأعطه لمطوّر الـ frontend (أو لأداة AI) مع رابط `/docs` أو ملف `openapi.json`.

---

## Role
You are a senior frontend engineer. Build the **review screen** of a financial-audit tool ("Cross-Casting"). The backend (FastAPI) already uploads a PDF/Excel/image, checks the arithmetic of every financial table (casting = totals vs their components, cross-casting = rows vs columns vs grand total) and returns findings. Your job is to let an auditor **see, understand, fix and track** each finding, and **export a PDF report**.

## Hard rules
1. **Never compute accounting arithmetic in the frontend.** Show the numbers exactly as returned (they are already formatted strings, e.g. `"-85,978.00"`).
2. **Never compose sentences yourself.** Every user-facing text is bilingual: `{ "en": "...", "ar": "..." }` (or `{ "en": [...], "ar": [...] }` for lists). Pick the key by the UI language.
3. **Arabic = RTL.** Layout must mirror in `ar`. Numbers, file names and IDs stay LTR (`dir="ltr"` on those elements, right-aligned in RTL) — otherwise a minus sign jumps to the wrong side.
4. `location.page` is only *where to look* in the source. Do not build any page-number comparison.
5. The PDF is generated by the backend — just download it, don't generate PDFs client-side.

## Configuration
- Base URL from env (`VITE_API_URL`, default `http://localhost:8001`). Backend CORS allows only origins listed in its `CORS_ORIGINS` — ask the backend owner to add your origin.
- No authentication at the moment.

## Flow
1. **Upload** — `POST /analyze` (multipart, field `file`; PDF / .xlsx / .xls / PNG / JPEG; max 100 MB; PDF max 100 pages) → `202 { job_id, status: "QUEUED" }`.
   Folder/zip: `POST /analyze/batch` (field `files`, repeated) → `{ batch_id, jobs[] }`; progress at `GET /batches/{batch_id}`.
2. **Poll** — `GET /jobs/{job_id}` every 2–3 s until `status` is `COMPLETED` or `FAILED` (`QUEUED → PROCESSING → COMPLETED|FAILED`). Show `stage` as progress text. On `FAILED` show `error_message` and a **Retry** button (`POST /jobs/{id}/retry`; warns that statuses reset to `open`). Large PDFs can take several minutes (one AI call per page) — show progress, don't time out.
3. **Review** — `GET /jobs/{job_id}/review` (everything) · `/casting` (casting only) · `/cross-casting` (cross-casting only). Optional `?status=open|acknowledged|resolved`. Returns `409` until the job is `COMPLETED`.
4. **Resolve** — `PATCH /jobs/{job_id}/issues/{issue_id}` body `{ "status": "open" | "acknowledged" | "resolved" }`. After a change, update that item locally and refresh counters (or re-fetch `/review`).
5. **Export** — `GET /jobs/{job_id}/review/pdf?lang=ar|en&scope=all|casting|cross_casting|verification&status=...` → `application/pdf` attachment. Use it from a normal link/`window.open` or fetch → blob → download. Default `lang` = current UI language.

Other useful endpoints: `GET /jobs` (list; filters `status`, `has_errors`, `batch_id`, paging `page`/`page_size`), `GET /jobs/{id}/file` (presigned URL of the original file — use it for "Open source"), `GET /dashboard/stats`, `GET /health`.

### Field semantics
- `priority`: 1 = fix first, ranked over the whole job (stable when filtering). Tables are already ordered by their best item; items inside a table are by `priority`.
- `category`: `casting` | `cross_casting` | `verification` (OCR vs AI-reader disagreement) | `other`.
- `check`: `vertical` (total vs its lines) · `horizontal` (row total vs its columns) · `trial_balance` · `row_vs_col` · `row_vs_grand` · `col_vs_grand` · `ocr_vlm` · `other`.
- `values[0]` vs `values[1]` are the two compared sides (labels included); `delta = values[0] − values[1]`; `direction`: `first_higher | first_lower | equal | n/a`. For `ocr_vlm` the values are text, `delta` is `null`.
- `severity`: `critical | high | medium | low` · `status`: `open | acknowledged | resolved`.
- `location.section`: the block the row belongs to (e.g. `"Balance as on 1 January, 2024"`, `"Accumulated depreciation and impairment:"`) — the same row label often appears several times in one note, so always show it next to `row` ("Currency translation adjustments — under: Balance as on 1 January, 2024").
- `location`: PDF/image → `page`, `row`, `column`, `bbox`; Excel → `sheet`, `cell`, `row`, `column`. `relation` is the formula (e.g. `Total assets = Cash + Inventory`) — show it in a monospace LTR block. Any field can be `null`: render only what exists.
- `summary` counts the whole scope regardless of the `status` filter (use for tab badges); `tables` honours the `status` filter. `is_clean` = no **open** item in scope.
- `coverage` makes "no errors" meaningful — always show it ("92 tables, 516 comparisons checked"). `coverage.pages_skipped` lists pages not read because OCR showed no financial table on them (cover, auditor's report, policy text) — show them (e.g. "22 narrative pages skipped: 1, 2, 6 …") so the reviewer can spot-check.
- `GET /jobs/{id}/file` → `presigned_url` is directly openable in the browser (signed for `MINIO_PUBLIC_ENDPOINT`); for PDFs append `#page={location.page}` to jump to the page.
- `related`: consequences merged into this finding — show as a small list under the card.

## Screens / components to build
1. **Upload + progress** — drag & drop; stage text while `PROCESSING`; failure state with retry.
2. **Review page header** — file name, `conclusion` banner (green if `is_clean`, red otherwise), counters from `summary` (total / open / acknowledged / resolved, casting vs cross-casting, by severity), `coverage`, language switch (ar/en), **Export PDF** button (uses current language and current tab as `scope`).
3. **Tabs/filters** — All · Casting · Cross-casting (+ Verification when `summary.verification > 0`); status filter (open / acknowledged / resolved); optional severity filter (client-side).
4. **Findings grouped by table** — collapsible group per table: name, page/sheet, `max_severity` badge, `counts`. Cards inside, in the order received.
5. **Finding card** — priority number, severity badge, status badge, `title`; location line; the compared **values side-by-side with the difference highlighted** (arrow/colour from `direction`); `relation`; `explanation`; collapsible **Likely causes**, **Hints** (only if non-empty) and **Steps to resolve** (ordered list); `related`. Actions: *Mark resolved*, *Mark acknowledged (false alarm / accepted)*, *Reopen*; optional **Open source** (use `/jobs/{id}/file` presigned URL, jump to `location.page` for PDFs).
6. **Empty / clean state** — when `tables` is empty show the `conclusion` and the coverage.
7. A collapsible **How to resolve** panel from `how_to_resolve`.

## Behaviour details
- Status change: optimistic update, roll back with a toast on error; disable the buttons while the request is in flight.
- Group counters (`counts.open`) and `summary` must update after a status change.
- Keyboard: `j/k` next/previous finding, `r` resolve, `a` acknowledge (nice to have).
- Persist the chosen language and last tab in `localStorage`.
- Responsive: cards stack on mobile; the two compared values stay readable (wrap, don't truncate).
- Accessibility: severity/status must not rely on colour alone (include the text label); `lang`/`dir` attributes set on the root.

## Errors to handle
`400` invalid id · `404` job/issue not found · `409` job not completed yet (keep polling) / job still running on retry · `413` file too large · `415` unsupported type · `422` bad query value · `503` from `/health` when the database or storage is down.

## Acceptance criteria
- Uploading a PDF ends on the review page without manual refresh.
- Switching language flips direction and every text comes from the API's `ar`/`en` (no hard-coded finding text).
- Negative numbers display as `-85,978.00` in both directions.
- Marking an item `acknowledged` moves it out of the *open* filter and updates the counters; reloading the page keeps it (it is persisted by the backend).
- "Export PDF" downloads a file whose language and scope match the screen.
- Works with 0 findings, with 1 table and with 90+ findings (virtualise or collapse groups by default when there are many).

## Context the UI should communicate (do not hide it)
The checker is strict and sometimes flags a line that is **not meant to be a sum** of the lines above it (summary tables, segment tables, tables mixing two years). The reviewer must be able to mark such findings **acknowledged**; the step text already says so. Do not auto-resolve anything and do not remove findings from the list.
